## 1. Introduction

Guru99 Bank v4 is a demo internet-banking application used for QA practice. A bank manager logs in and manages customers, accounts, transactions and statements. This Test Plan describes the scope, approach, environment and deliverables of a complete manual testing cycle executed against the live v4 application, following the Software Testing Life Cycle (STLC) the way it is applied in a real company QA team.

## 2. Objectives

- Verify the functional behavior of all manager-facing modules against the documented field-validation rules of Guru99 Bank v4.
- Detect, document and report defects with reproducible steps and evidence.
- Produce a complete, interview-ready QA artifact set: Test Plan, Test Scenarios, Test Cases, execution results, Bug Reports, RTM and Test Summary Report.

## 3. Scope

### 3.1 In scope (functional modules)

1. Manager Login / Logout
2. New Customer
3. Edit Customer
4. Delete Customer
5. New Account
6. Edit Account
7. Delete Account
8. Deposit
9. Withdrawal
10. Fund Transfer
11. Change Password
12. Balance Enquiry
13. Mini Statement
14. Customised Statement

### 3.2 Out of scope

- Performance, load and security (penetration) testing
- Automation (this cycle is manual only)
- Admin-side/back-office behavior not exposed in the v4 UI
- Email delivery of credentials (Guru99 platform behavior, not the application)

## 4. Test Approach

- Black-box, requirements-based functional testing with boundary-value and negative-test design for every input field.
- Test design techniques: equivalence partitioning, boundary value analysis, negative testing, state transition (account balance before/after transactions).
- Execution is manual against the live application in a desktop Chrome browser; every executed case records its actual observed result, and mismatches with the expected result are raised as defects with screenshots.
- End-to-end flow: create a customer → open an account → deposit → withdraw → fund transfer → statements, so later modules consume data created by earlier tests (as in a real project).

## 6. Entry and Exit Criteria

### Entry criteria
- Demo access credentials received and login verified.
- Test Plan reviewed and test cases designed.

### Exit criteria
- 100% of designed test cases executed.
- All defects logged with severity, priority, steps and evidence.
- Test Summary Report produced with pass/fail metrics and defect summary.

## 10. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Demo credentials expire after 20 days | Complete the full cycle immediately after receiving access |
| Demo site is shared and data can be reset by Guru99 | Create own test data at the start of execution; re-verify IDs before use |
| Demo site instability/downtime | Record actual behavior observed; retry bounded times only |
