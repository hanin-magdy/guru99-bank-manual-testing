## 1. Introduction

Guru99 Bank V4 is a demo internet-banking application used for QA practice. A bank manager logs in and manages customers, accounts, transactions and statements. This plan covers the scope, approach, environment and deliverables for my manual testing of the live V4 application, following the Software Testing Life Cycle (STLC).

## 2. Objectives

- Check the behavior of all manager-facing modules against the field-validation rules of Guru99 Bank V4.
- Find and report defects with clear steps to reproduce and evidence.
- Produce a full set of QA documents: Test Plan, Test Scenarios, Test Cases, execution results, Bug Reports, RTM and Test Summary Report.

## 3. Scope

### 3.1 In scope (functional modules)

1. Manager Login / Logout
2. New Customer
3. Edit Customer
4. Delete Customer
5. New Account
6. Edit Account
7. Delete Account
8. Deposit
9. Withdrawal
10. Fund Transfer
11. Change Password
12. Balance Enquiry
13. Mini Statement
14. Customised Statement

V4 is tested in depth. V1, V2 and V3 are only compared with V4 on login, branding and available modules (see the Cross-Version Comparison sheet in the workbook).

### 3.2 Out of scope

- Performance, load and security (penetration) testing
- Automation (this cycle is manual only)
- Admin-side behavior not exposed in the V4 UI
- Email delivery of credentials (Guru99 platform behavior, not the application)

## 4. Test Approach

- Black-box, requirements-based functional testing with boundary-value and negative cases for every input field.
- Techniques: equivalence partitioning, boundary value analysis, negative testing, state transition (account balance before and after transactions).
- Tests are run manually on the live application in desktop Chrome. I record the actual result of every executed case, and any mismatch with the expected result is logged as a defect with a screenshot.
- End-to-end flow: create a customer, open an account, deposit, withdraw, transfer funds, check statements. Later modules use the data created by earlier tests.

## 6. Entry and Exit Criteria

### Entry criteria
- Demo access credentials received and login verified.
- Test Plan reviewed and test cases designed.

### Exit criteria
- 100% of designed test cases executed.
- All defects logged with severity, priority, steps and evidence.
- Test Summary Report produced with pass/fail numbers and defect summary.

## 10. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Demo credentials expire after 20 days | Finish the full cycle right after getting access |
| Demo site is shared and Guru99 can reset the data | Create my own test data at the start and re-check IDs before using them |
| Demo site is unstable or down | Record the behavior I see and retry only a limited number of times |
